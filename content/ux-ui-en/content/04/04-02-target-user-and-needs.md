# Target users and user needs

## Objectives

Students will be able to describe target users in relation to a task, distinguish an expressed request from an underlying need, and recognize the danger of optimizing for a single imagined “average user.”

## A target user is not a demographic label

> [!note] Key idea
> “University students aged 18–25” is too broad to support design decisions. Age or location alone rarely tells us what to bring forward in an interface, how to name an action, or how much help is needed. Describe target users through their situation, goal, prior knowledge, available time, device, and the consequences of an error.

“A student submitting an application for the first time, with little time to understand which documents are needed and worried about missing the deadline” is a usable description. It suggests that the system must clearly communicate requirements, the deadline, and successful submission. It does not mean everyone is exactly like this; it means we are designing the first version for this important situation.

## Requests, goals, and needs

An expressed request does not always reveal the underlying need directly. “Send more reminders” may reflect a need to avoid missing an important step. Notifications are one possible solution, but so are a deadline calendar, process status, advance notice, or a simpler task list. Accepting only the proposed feature can make us miss a better solution.

In research, therefore, ask: in what situation was the request made? What was the person trying to achieve? What consequence did they want to avoid? What workaround did they use? Express the need without specifying an interface form. “Users need to know for certain that their application is complete” is a need; “we need a green checkmark” is a solution idea.

## Primary and secondary actors

Several people may have different tasks within one process. The target user is the person whose main task you optimize for. A secondary actor might be an administrator checking information or someone providing support. If needs conflict, state whose takes priority on that screen. A student form supports the student's task, while still considering the administrator's need for complete, understandable information.

## Different abilities and circumstances

Consider different access circumstances in the target user description. Some people work on a phone with a poor connection; others use screen readers or magnification; some know the jargon, while others encounter it for the first time. You do not need a persona for every combination, but identify critical conditions that exclude people. If a task requires a mouse and a fast connection, the service's actual audience is narrower than we might think.

## Worked example

For a local event discovery project, the designer initially imagines a site for “young city residents.” Research reveals that the important distinction is how people plan, rather than their age: some spontaneously search for tonight's activities with little time, while others organize a group weeks ahead. These situations require different information. Spontaneous users need time, location, and availability immediately; organizers may prioritize group size, cancellation, and sharing. A semester project should choose a primary situation rather than try to solve both perfectly at once.

## Common misconceptions

| Statement | Clarification |
| --- | --- |
| “Every persona detail must be filled in.” | Record only details that change a design decision. |
| “If users request a feature, we must build it.” | The feature is their proposed solution; investigating the underlying goal and obstacle is the designer's job. |
| “Inclusion means a separate target group.” | Many accessibility decisions make the task more robust for the entire audience. |

## Review questions

1. What situation makes your project's main task especially important?
2. Which feature request might reflect a different, deeper need?
3. Who is the main user on a selected screen, and who is an affected secondary actor?
4. What circumstance could currently exclude some of your target users?

## Glossary

**Target user:** the user situation or actor whose task the solution is optimized for.  
**User need:** the value users want to obtain or the risk they want to avoid.  
**Primary actor:** the main user of the selected task.  
**Secondary actor:** a stakeholder participating in the process with another goal or task.
